# 文档目录

## 约定

* **`../README.md` 面向"怎么用"**：怎么跑、架构长什么样、产物在哪、已知限制。
* **`docs/` 面向"实现知识"**：与源码 docstring 同源的东西集中放这里，
  避免同一件事在两个地方各写一份然后漂移。
* 任何"实测结论"都要写**方法**（怎么测的）与**边界**（换了什么条件就不成立）。
  没有方法的数字是传说，下一个人会把它当事实引用。

## 为什么把协议细节放在 docs/ 而不是 README

README 的读者是"想把它跑起来的人"；协议细节的读者是"想改它的人"。
两者对同一段内容的需求完全不同 —— 前者要最短路径，后者要全部前提。
混在一起的代价是**两边都读得不顺**，最后谁都不去更新它。

## 写新文档前的三个问题

1. 这条知识**会不会因为平台改版而失效**？会 ⇒ 写清"观测日期 + 判据"，
   而不是把它写成永恒事实。
2. 这个数字是**实测**还是**估计**？估计必须标出来。本项目里
   `HR_REG_QUOTA_MAX` 的默认值就是估计（对比 Intern-Register-Tool 的
   40 是撞墙撞出来的）—— 混为一谈会让下一个人据此做错误决策。
3. 这条结论**换了什么条件就不成立**？写出来。例如"5 连发没有限流"
   只在"服务端正常时"成立，而服务端那次是 500（不是 429）。
