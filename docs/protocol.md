# Hark 注册协议（实测记录）

> 本文是**实现知识**：与源码 docstring 同源，集中一处才不会漂移。
> 面向"怎么用"的部分在仓库根的 [`../README.md`](../README.md)。

## 证据来源

| 来源 | 用途 |
|---|---|
| `hark.com-1.har`（83 条） | 登录页 + 注册申请三步的**请求/响应原文** |
| `hark.com-2.har`（133 条） | 设密码 → 会话 → 资料/额度/会话列表的原文 |
| 线上逐条复现（2026-10-07） | 上面两份 HAR 里**没有**的部分：邮件正文、magic link 形状、边界值 |

HAR 里**没有 cookie**（导出时被脱敏），所以会话机制是从 `Set-Cookie` 的
**响应头**和实测复现里得到的，不是从 HAR 里读出来的。

## 链路（7 步，全程纯 HTTP）

```
① POST {hark}/api/auth/account-discovery   {"identifier","kind":"email"}
     → 200 {"exists":false,"hasPassword":false}
② POST {hark}/api/auth/signup-age          {"identifier","kind","birthday"}
     → 200 {"accepted":true}                ← 年龄门
③ POST {hark}/api/auth/sign-in/magic-link  {"email","callbackURL","errorCallbackURL"}
     → 200 {"status":true}                  ← 发信（对**不存在**的邮箱也发 ⇒ 这就是注册）
④ 收信（CF Worker 临时邮箱）
     发件人 0101…@mailer.hark.com   主题 "Your Hark sign-in link"
     链接   https://auth.hark.com/api/auth/magic-link/verify?token=…&callbackURL=…
⑤ GET  该链接 → 302 + Set-Cookie
     __Secure-hark.session_token=<token>.<hmac>   （Domain=hark.com, HttpOnly, Secure, SameSite=Lax, Max-Age=30d）
     __Secure-hark.region=us
     __Secure-hark.access=app
⑥ POST {hark}/api/auth/set-password        {"newPassword":"…"}
     → 200 {"status":true}                  ← **一次性**
⑦ POST {hark}/api/auth/sign-in/email       {"email","password"}
     → 200 {"redirect":false,"token":"…","user":{…}}   ← 密码登录，换一条**全新会话**
```

之后的只读校验（本项目记为 `app` 阶段）：

```
GET  {hark}/api/auth/get-session      → {"user":{…},"session":{…}}
GET  {hark}/api/profile               → 资料（含 birthday/age/origins/admission）
GET  {hark}/api/billing/summary       → 额度结构
POST {hark}/api/billing/options       {"storeContext":null} → 套餐清单
GET  {hark}/api/conversations         → 会话列表（新账号已自带 1 条空会话）
```

## 两个域名

| 域名 | 用途 |
|---|---|
| `hark.com` | 站点 API（`/api/auth/*` 与 `/api/*` 都能打） |
| `auth.hark.com` | **magic link 的校验端点只在这里**（邮件里给的就是它） |

cookie 的 `Domain=hark.com`（**不带前导点**）⇒ 两个 host 共享会话，所以
第⑥步在 `hark.com` 上打、第⑤步在 `auth.hark.com` 上打，会话是通的（实测）。
本项目把两个 base 都做成配置项（`HR_HARK_BASE` / `HR_AUTH_BASE`），
**不是笔误**。

## 边界值与实测判据

### 年龄门（`signup-age`）

2026-10-07 按"年"逐档扫（生日取当天日期，故 age 精确）：

| 生日 | 周岁 | 结果 |
|---|---|---|
| 2005-10-07 | 21 | `200 {"accepted":true}` |
| 2008-10-07 | **18** | `200 {"accepted":true}` ← 刚好过 |
| 2009-10-07 | 17 | `403 {"code":"CARD_VERIFICATION_REQUIRED"}` |
| 2020-01-01 | 6 | `403 {"code":"CARD_VERIFICATION_REQUIRED"}` |
| 1900-01-01 / `"bad"` | — | `400 {"code":"INVALID_BIRTH_DATE"}` |

⇒ 门槛是**满 18 岁**；未满 18 不是"注册失败"，而是被要求**绑卡**。
所以 `config.validate()` 在启动阶段就拦未成年的生日 —— 否则**每个账号**
都要白撞一次这个 403。

### 密码策略（`set-password`）

| 输入 | 结果 |
|---|---|
| `abc` / `Ab1!` | `400 {"code":"PASSWORD_TOO_SHORT"}` |
| `12345678`（8 位） | 通过长度检查（进入下一步 ⇒ 撞 `PASSWORD_ALREADY_SET`） |
| 15 位随机（HAR 里那条） | `200 {"status":true}` |

⇒ 服务端**只卡长度（≥8）**，没观测到大小写/数字/符号的强制要求。
但本项目生成密码时仍按四类字符各取一个（代价为零，而"平台突然加策略"
会让整批注册失败）。

🔴 **`set-password` 是一次性的**：第二次调用返回
`400 {"code":"PASSWORD_ALREADY_SET"}`。实测确认（在同一个会话里连打 8 次，
只有第一次成功、其余全是这个码）。所以：

* 重试这一步是**错的**（会把一个已完成的步骤报成失败）；
* 但把它当"成功"也要**标注出来** —— 若密码不是我们设的，台账里那一列就是错的。

### 密码登录

| 输入 | 结果 |
|---|---|
| 正确密码 | `200 {"redirect":false,"token":"…","user":{…}}` |
| 错误密码 | `401 {"code":"INVALID_EMAIL_OR_PASSWORD"}` |

⚠ **不需要** `Origin` / `Referer`（实测去掉也 200）。本项目仍然带上，
因为那是浏览器的真实行为，而"少一个头也成功"不等于"平台不看这个头"。

### 邮箱格式

`account-discovery` 对 `not-an-email` 这种串也返回 `200 {"exists":false}`
（服务端不校验格式）。所以它**不能**当"注册前置校验"用，只能当
"走注册还是走登录"的分支依据。

### 域名门

**没有**。自有域名直接过。这一条值得单独写出来，因为
Intern-Register-Tool 那边吃过 `A0232` 域名门的亏（换邮箱源、可插拔邮箱源
那一整套抽象就是为它做的）。**hark 不需要那套抽象**，所以本项目只有
一个邮箱源。

## 收信：CF Worker 临时邮箱

与 Intern-Register-Tool **共用同一台 Worker**（同一个 CF 账户），
所以那边的坑在这里同样成立：

* 收信一律走 `/api/inbox?email=`（按收件人索引），**不要** `/admin/all`
  （全表扫描，既烧 D1 读配额，又会被别人的邮件挤出"最新 N 条"窗口）。
* 5xx 必须**重试而不是判死** —— Worker 会间歇性抛 Cloudflare `Error 1101`，
  而那时邮件其实好好躺在库里。
* 不带浏览器 UA 的请求会被 CF 边缘直接 403（`error code: 1010`）。

hark 特有的三点：

1. **`extracted_json` 的状态在 2026-10-08 变了**：之前是空的（`[]`，Worker 没为这个
   发件人配规则），**现在 Worker 侧已有规则**（D1 `rules` 表，remark =
   `Hark 魔法链接（注册 / 登录）`），新邮件会带链接。本工具仍**自己从正文抽**，
   因为它要覆盖两类漏网情形：规则落库之前已入库的历史行，以及 Worker 规则缓存
   （`RULES_TTL_MS = 60s`）窗口内刚插入的规则。
   实测 `body`（纯文本）里 `&` 是原样的，而 `raw_html` 里是 `&amp;` ——
   两条路都要 `html.unescape`，且都要剪掉粘在尾部的标点（邮件把同一个链接
   写了两次，一次在 Markdown 括号里）。
2. **`received_at` 是毫秒**（`1791375033474`，与同一条记录的
   `receivedDateTime` ISO 串是同一时刻）。`since_ts` 用它做"只看这之后到的信"
   的下限 —— 单位错了过滤会**全部失效**，而旧链接**仍然有效**，
   所以这个 bug 不会当场炸，只会让"重跑"变得不可靠。
3. 🔴 **表会被别人的推广邮件挤爆**（2026-10-07 实测）：D1 的 `emails` 表总量上限是
   **100 行**（Worker 的 `MAX_MESSAGES_TOTAL`），按 `id` 滚动。当天一个 Grok 推广
   轰炸（~1 封/分钟，同一主题 98 封）占掉了 100 行里的 98 行，于是**别人的激活邮件
   被挤掉**：hark 的 7 行掉到 2 行（正在写本文时掉的）。
   两件事让 hark 这条链几乎不会踩到：轮询间隔只有 0.8s（拿到就读），
   而带 `extracted_json` 的行受 Worker 的**独立保护窗口**保护。
   但只要“等信”变成了分钟级（比如人工介入），就要知道邮件可能已经不在了。

### 邮件到达耗时

| 观测 | 值 |
|---|---|
| 单账号：magic-link 请求 → 邮件可读 | **261ms / 285ms**（两次实测） |
| 轮询次数 | 1 次（间隔 0.8s，即第一次就命中） |

⇒ hark 的投递比 OpenXLab 快得多（那边实测 6.02s）。**等信不再是整链瓶颈**，
真正的耗时大头变成了 `mailbox`（建地址）和 `verify`（校验链接）——
见下面的耗时分解。

## 限流与配额：实测

这一节刻意写得**保守**，因为"没测到"不等于"没有"。

### 已测到的

| 观测 | 方法 | 结果 |
|---|---|---|
| **`sign-in/email` 限流** | 同一账号连打 5 次（无间隔） | 第 1、2、3 次 **200**；第 4、5 次 **`429 RATE_LIMITED`** |
| magic-link 突发 | 同一地址连打 **5 次 / 2.5s** | **全部 200**，且**收到 5 封邮件**（无去重、无 429） |
| 连续 4 路并发注册 | `--count 4 --workers 4 --producers 4` | **4/4 失败**，但**不是限流** —— 见下 |

### 🔴 `sign-in/email`：3 次 / 10s（本项目唯一测出数字的限流）

方法：拿台账里一个**已知可用**的账号，连打 5 次登录，逐次记录时刻与状态码。

```text
第 1 次  t=2.27s  HTTP 200
第 2 次  t=4.34s  HTTP 200
第 3 次  …        HTTP 200
第 4 次  …        HTTP 429 {"message":"Too many requests. Please try again later."}
第 5 次  …        HTTP 429
```

判据：单个请求本身要 **~2.1s**，所以前三次落在同一个 10s 窗口内、
后两次被拦 ⇒ **3 次 / 10s**。这个数字与 better-auth 的默认自定义规则
`"/sign-in/email": { window: 10, max: 3 }` **完全吻合**，可信度较高。

**为什么这条必须写进文档，而不是"知道就好"：**

1. `--workers 4` 会让 4 个账号在 ~2s 内各登录一次 ⇒ **第 4 个必然 429**。
   而 429 在报告里是 `quota`，很容易被读成"这个账号/这个出口被封了" ——
   那是一个**假阴性**（账号其实好好的）。
2. `tools/ops/verify_accounts.py` 默认把整本台账连成一片打过去，
   不加限速的话它会报"你的账号全挂了"。

所以消费者侧有两道处理（见 `src/pipeline.py`）：

* **滑动窗口限速**（`SlidingWindow`，默认 3 次 / 10s）—— 与平台的判据同构。
  刻意**不用"最小间隔"**：平台限的是"窗口内最多 3 次"，而固定间隔在请求比
  预期快时会把第 4 次挤进窗口。
* **429 退避重试**（默认最多再试 3 次）—— 登录的 429 是**自愈**的（窗口滑出就好），
  与"注册配额"不是一回事：后者（若真存在）越试越糟，所以生产者那侧是**停整批**，
  而这里只是等一等。

### 🔴 10 批全链路实测（2026-10-08）：43/50，并测出**两种** 429

配置：5 个槽位出口（`--producers 5 --workers 5`），**10 批 × 5 个账号 = 50 个**，
批次**串行**、批内并发。（不并行跑 10 个进程的原因：登录限流是服务端按 IP 计的，
而我们的限速器是**进程内**的 —— 10 个进程会各算各的，把 3 次/10s 打穿。）

| 批次 | 结果 | 墙钟 | 备注 |
|---|---|---|---|
| 1–5 | **5/5 全绿** | 10.2 ~ 12.1s | 零失败 |
| 6 | 2/5 | 10.3s | 3 个**注册侧** 429 |
| 7 | 4/5 | 11.4s | 1 个 TLS 抖动（`SSLError`） |
| 8–10 | 4/5 × 3 | 19.7 ~ 21.8s | 各 1 个**登录侧** CF 429（重试 4 次仍失败） |

合计 **43/50（86%）**，5/10 批完全干净。按出口：`7902` 10/10 全绿；
`7901` 最差（8/10，3 个失败全在最后 3 批）。

#### 两种 429 的形状完全不同，不能混为一谈

| | 注册侧（批次 6） | 登录侧（批次 8–10） |
|---|---|---|
| 响应体 | 短文本 `Too many requests. Please try again later.` | **Cloudflare 的 HTML 错误页**（`<!doctype html>…no-js ie6 oldie…`） |
| 命中范围 | **3 个不同出口同时中**（7903/7905/7904） | **只在一个出口上**（7901，连续 3 批） |
| 推断 | ~~不是 per-IP~~ → **是 per-IP**（见下一节；当时推错了） | CF 边缘的 per-IP 限流 |
| 恢复 | 几分钟后自行恢复（02:41 重测已正常） | 未观察到自行恢复（重试 4 次、跨 ~17s 仍 429） |

**当时的结论与后来的修正**：

* 登录侧的 CF 429 是**出口维度**的 ⇒ 正确做法是**换出口**，而不是在原地重试。
  ✅ **已改**（`pipeline._rotate_login_slot`）：撞 429 先换出口，换不动才退避。
  台账里 `proxy` 记**最终**出口、`proxy_rotated` 记换过的路径。
* 注册侧的 429 **当时被判成“不是 per-IP”**，依据是“3 个不同出口同时中”。
  🔴 **那个推理是错的** —— 下一节用对照实验推翻了它。
* 出口是**稳定**的：每个槽位连打 4 次 `api.ipify.org`，四次都是同一个 IP
  ⇒ “5 个出口”真的是 5 个不同 IP，不存在上游 NAT 把几个节点合并成一个出口的情况。

#### 🔴 对照实验：注册侧的 429 其实是 per-IP（2026-10-08 复测）

工具：`tools/probes/probe_register_limit.py`（**不校验链接**，所以不建任何账号）。

```text
#  1  discovery=200 signup-age=200 magic-link=200
#  2  discovery=200 signup-age=200 magic-link=200
#  3  discovery=200 signup-age=200 magic-link=429      ← 同出口第 6 次（含前一次探测的 3 次）

B1 换收件域名 @<另一个自有域名>（同出口）: 仍 429      ← 不是按域名键
B2 换出口 7902（同域名）:                 **通过**    ← 是按 IP 键
B3 只打 discovery（只读）:                通过        ← 限的是写端点 magic-link
```

| 问题 | 答案 | 依据 |
|---|---|---|
| 限哪个端点？ | **`magic-link`**（discovery / signup-age 不限） | B3 |
| 按什么键？ | **客户端 IP** | B2 换出口立刻通过；B1 换域名没用 |
| 额度多大？ | 约 **5 次 / 分钟 / IP**（第 6 次 429） | 阶段 A + 前一次探测累计 |
| 窗口多长？ | **60s**（实测：t+43.8s 仍 429、t+55.1s 通过；见下） | `--measure-window` |

**那次错推的教训（比结论本身值钱）**：

> 批次 6 里 3 个出口**同时**中 429，我据此判定“不是 per-IP”。
> 但每个出口在前 60s 里都积了 ~5 次（每批 1 次 × 5 批）—— 它们**同时**触顶，
> 只是因为它们的**历史相同**。**同时性 ≠ 同一个键。**
> 一个“同时发生”的观测，区分不了“共享一个计数器”与“各自独立但节奇一致”。
> 要定性必须**只变一个变量**（这里：同出口换域名、同域名换出口）。
>
> 代价：那个错结论直接导出了一个错的参数（“每进程全局最小间隔 1s”），
> 而它**两头都不对** —— 既拦不住单出口超限（5 出口轮转时每个会跑到 12 次/分），
> 又在小批量里白花了 ~2–3s（把 5 个注册申请串行化）。

#### 窗口长度：实测 60s（同一工具的 `--measure-window`）

```text
🔴 第 6 轮命中（magic-link）—— 开始按 10s 粒度探测恢复
  t+ 10.9s  仍 429
  t+ 21.9s  仍 429
  t+ 32.8s  仍 429
  t+ 43.8s  仍 429
  t+ 55.1s  通过 ✅

第二段（对照）：再打到 429，然后等 60s 只探一次 → 通过 ✅ 与第一段自洽
```

⇒ 窗口 ≈ **60s**（突发那 5 个成功请求几乎同时，所以“窗口滑出”≈“恢复通过”）。

🔴 **对照段的用处**：有个问题一开始没法排除 —— “被 429 拒掉的尝试**是否也计入
窗口**”？如果计入，那每个失败的探测都会把窗口往后推，测得的值就只是个**上界**。
对照段重打到 429、**不探测**、等满 60s 再只探一次：通过 ⇒ 失败探测**不推窗口**，
所以第一段是干净的下界式测量（区间 (43.8, 55.1] 与 60s 相容）。

⇒ `HR_REGISTER_WINDOW_S=60` 从“保守取值”升级成**实测值**。

**与批次的对照（2026-10-08 复跑 5 批）**：5 批 × 5 账号连跑，
每个出口各拿到 **5 次注册 / 40s**（08:06:30→08:07:10），**零 429**；
随后第 6 批在 **+663s** 才跑，所以也零 429。
⇒ 与“约 5 次/分/出口”完全相容（5 次/40s 正好卡在额度上，第 6 次/60s 才被拒）。
🔴 但这也暴露一个**设计边界**：限速器是**进程内**状态，
而每批都是一次新的 `run.py` 进程 ⇒ 它保护不了“紧接着跑第 6 批”。
（该次之所以没踩到，只是因为那 11 分钟让窗口自己滑出了。）

**修正后的实现**：注册申请改用**按出口的滑动窗口**（`REGISTER_MAX_PER_WINDOW=4` /
`REGISTER_WINDOW_S=60`，略保守于观测到的 5），与登录侧同构。实测效果：

| 5 账号一批 | 改造前（全局 1s） | 改造后（按出口） |
|---|---|---|
| 批墙钟 | 10.2–12.1s | **8.7 / 8.9 / 9.0s** |
| 每账号 | 2.04–2.42s | **1.75–1.80s** |

而且它现在**真的**在拦：有一次探测刚把某个出口打到 429，紧接着的批里那个
出口上的账号在闸门里等了 ~7s（**没有**报 429）—— 那是“等”换掉了“失败”。

### 🔴 域名门：自有域名里有的收不到 hark 的信（2026-10-08）

有一个自有域名在 Worker 的 `DOMAINS` 里、邮箱也能建出来，但 hark 的 magic link
**从来没到**。现象是：

```text
等 120s 没等到 magic link 邮件（打了 116 次收信接口）
```

—— 每个账号白等 **120 秒**，而且错误分类是 `rejected`（“邮件没到”），
看起来像投递慢，实际是**这个域名收不到**。

所以要跑批量之前先用 `tools/probes/probe_domains.py` 过一遍域名（它**不验证链接**，
所以不会建任何账号 —— hark 的账号是在 `magic-link/verify` 那一步才建的）。
已实测可用的自有域名写在 `.env` 里（不进仓库）—— 换域名后重跑一次本工具即可。

### 那次"4/4 失败"到底是什么（重要）

2026-10-07 22:04 的一次 4 路并发跑批全部失败，`error_kind=network`，
错误是 `HTTP 500：(空响应体)`，失败在 `register` 阶段。逐项排查：

| 探针 | 结果 |
|---|---|
| `account-discovery`（同一出口 IP、同一时刻） | **200** |
| `signup-age`（同上） | **200** |
| `sign-in/magic-link`（同上） | **500**，`Content-Type: text/plain`，**空 body** |
| 换邮箱域名（公共邮箱 / 另一个自有域名 / 全新地址） | 全部 **500** |
| 已有账号（`exists:true`）的 magic-link | **500** |
| 同一时段走本地代理出口 | **500**（⚠ 见下） |
| 30 分钟后重测 | **仍然 500**（持续，不是瞬时抖动） |

⇒ 判据是：**换域名、换收件人、换"新号/老号"都不变，而另外两个端点照常 200**。
所以这不是"我们被封了"，也不是"域名被拦"，而是**服务端 magic-link 这条
（发信）链路本身在 500**。5xx 的分类是 `network`（可重试），这是对的。

> ⚠ **一个没有排除干净的可能**：那次"走本地代理"其实**并没有换出口 IP**
> （实测两个路径的 `api.ipify.org` 都是同一个 `104.194.8.36`）——
> 本地 Clash 的混合端口对外仍是同一个 IP。所以"出口维度限流"这个解释
> **没有被证伪**。要真排除它，必须用一个**出口 IP 确实不同**的代理重测。
> 这正是 `tools/probes/probe_magic_link.py` 存在的理由：它把"控制组 / 对照组 /
> 换出口"三件事做成一次对照实验，并把那个前提写进了输出里。

**结论：这条记录不能用来推断 hark 的注册限流。** 要测限流，必须在
服务端正常的时候跑，并且用**递增并发**（1 → 2 → 4 → 8）看第一个出现
非 200 的点。本项目还没有这个数据，所以：

* 注册申请的限速已改成**按出口的滑动窗口**（`HR_REGISTER_MAX_PER_WINDOW=4` /
  `HR_REGISTER_WINDOW_S=60`）—— **实测值**，取代了旧的“每进程全局最小间隔”；
* `HR_REG_QUOTA_MAX`（本地窗口上限）默认 **50** —— 它是**爆炸半径上限**，
  不是服务端配额（真正的限流是上面那两个按出口的窗口）；
  旧默认 20 被现实跨过（一天成功 53 个），已上调；
* 报告里对 5xx 的措辞是"network（可重试）"，不会说成"被封"。

> 参照：Intern-Register-Tool 那边的 `REG_QUOTA_MAX=40` 是**撞墙撞出来的**，
> 而它的封禁是 IP 维度、窗口 > 68.2h。本项目**没有**任何证据支持把那个
> 经验搬过来，所以不搬。

### 失败后的处理

`pipeline.QUOTA_STREAK_STOP = 2`：连续两次**服务端配额拒绝**就停整批，
剩余任务标 `quota_guard`（**一个请求都没发**）。取 2 而不是 1，是因为单次
429 完全可能是抖动。

⚠ 这条只作用于**生产者**（注册申请）。消费者（登录）的 429 走另一条路 ——
退避重试，见上面「`sign-in/email`：3 次 / 10s」。两者**不能统一**：
一个是"继续打只会更糟"，另一个是"等一会就好"。

## 耗时分解（单账号，实测）

一次成功注册的完整分解（`--count 1`，2026-10-07）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| `mailbox` | 2422ms | CF Worker 建地址 + D1 写入 |
| `register` | 3401ms | discovery + signup-age + magic-link（三个写请求） |
| ├ `mail_wait` | 285ms | 邮件到达（轮询 1 次） |
| └ `verify` | 3710ms | **校验 magic link**（302 + 建会话）—— 比预想慢得多 |
| `password` | 292ms | set-password |
| `login` | 1417ms | sign-in/email（换新会话） |
| `app` | 904ms | get-session + profile + billing + conversations |
| **合计** | **12431ms** | |

⇒ 两个反直觉之处：

1. **等信只占 285ms**（对比 OpenXLab 的 6020ms）。整链最该优化的不是收信。
2. **`verify` 花 3710ms** —— 一个 302 竟然比 `register` 的三个请求加起来还慢。
   它是服务端建会话 + 写库的那一步。要压缩它只能靠并发掩盖（本项目就是这么做的）。

## 会话与凭据

| 项 | 值 |
|---|---|
| cookie 名 | `__Secure-hark.session_token`（值 = `<token>.<hmac>`） |
| 有效期 | `Max-Age=2592000`（30 天），`session.expiresAt` 是**服务端给的**权威值 |
| `session.token` | 与 cookie 的前段**实测相等**（台账里存这一段） |
| `__cf_bm` | Cloudflare 的 bot 管理 cookie，**与业务无关**，不进台账 |

## 不做什么

* **不碰付费环节**：领的就是平台公开提供的免费额度，不篡改额度、不绕过支付。
* **不逆向混淆 JS**：整条链路都是标准 JSON API，没有验证码、没有 WAF 解盾
  （对比 Intern-Register-Tool 必须用真浏览器解阿里云验证码）。
  所以本项目**零浏览器、零 playwright 依赖**。
* **不做批量刷取**：本地配额闸门（`HR_REG_QUOTA_MAX`）默认拦在 50/24h，
  要放开得**显式**加 `--ignore-quota`。
